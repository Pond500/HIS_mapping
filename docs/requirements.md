# ความต้องการและการตัดสินใจ — HIS Mapping POC (Multi-agent)

> สรุปจากการคุยรายละเอียดความต้องการ วันที่ 2026-09-12
> เอกสารนี้เป็นข้อตกลงร่วม: ถ้าจะเปลี่ยนการตัดสินใจข้อไหน ให้แก้ที่นี่ก่อนแก้โค้ด

## เป้าหมายหลัก

> **ระบบรับไฟล์ข้อมูลผลตรวจสุขภาพจากที่ไหน หน้าตาแบบไหนก็ได้ แล้วใช้ agent ช่วยแปลงลงระบบของเราได้อย่างแม่นยำ**

- **ประเภทงาน:** POC สำหรับนำเสนอหน่วยงานกลาง (เช่น สคร. / กรมควบคุมโรค) ที่รับไฟล์จากหลายโรงพยาบาล
- **ระยะเวลา:** 3 สัปดาห์ แล้ว demo สด

## กฎเหล็ก

> **ทุกค่าที่เข้าระบบต้อง "ถูก" หรือ "ถูกจับให้คนดู" ห้ามมีค่าผิดหลุดเข้าไปเงียบ ๆ**

## การตัดสินใจ

|---|---|---|

| D2 | ข้อมูลที่ใช้ | ข้อมูลสังเคราะห์ทั้งหมด ไม่มีข้อมูลคนไข้จริง |

| D4 | รูปแบบนำเสนอ | Demo สด มี **โหมด replay** (เล่นคำตอบ AI ที่บันทึกไว้) เป็นแผนสำรอง |
| D5 | ตัวเลขเวลาที่ประหยัด | ไม่มีตัวเลขเวลาเดิมจากเจ้าหน้าที่ → ทำ**ตัวคำนวณบน dashboard** ให้ผู้ฟังกรอกตัวเลขของหน่วยงานตัวเอง ห้ามอ้างตัวเลขที่ไม่มีที่มา ส่วนความแม่นยำและต้นทุนใช้ค่าที่วัดได้จริง |
| D6 | Mapping | **สองชั้น**: พจนานุกรมกลาง + mapping เฉพาะของแต่ละโรงพยาบาลที่ใช้ทับของกลางได้ (ค้นของโรงพยาบาลนั้นก่อน) mapping ที่ยืนยันใหม่บันทึกเป็นของโรงพยาบาลนั้น การเลื่อนขึ้นเป็นของกลางต้องมีคนกด |
| D7 | ขอบเขตข้อมูลเข้า | **ระดับ 1:** CSV / XLSX / XLS หน้าตาแบบไหนก็ได้ (Long/Wide, หัวไทย/อังกฤษ, หัวรายงาน, หลาย sheet, header หลายแถว, ชื่อ lab/หน่วย/วันที่ต่างกัน) |
| D8 | ความแม่นยำ | สิ่งที่ระบบผ่านเองต้องถูก **≥ 99.5%** / ระบบทำเองได้ **≥ 70%** สำหรับโรงพยาบาลใหม่ และ **≥ 95%** สำหรับโรงพยาบาลเดิมรอบถัดไป (วัดบนชุดสอบที่ล็อกไว้) |
| D9 | ผู้ใช้ | บทบาทเดียว: **เจ้าหน้าที่หน่วยงานกลาง** เป็นทั้งคนอัปโหลดและคนยืนยัน หน้าจอยืนยันต้องแสดงหลักฐาน (ค่าตัวอย่างเทียบกับช่วงค่าปกติ, หน่วย, ความเห็นของ Mapper/Verifier เป็นภาษาไทย) และมีปุ่ม "ไม่แน่ใจ ข้ามไว้ก่อน" |
| D10 | โมเดล AI | **OpenRouter + โมเดลราคาถูก** ตั้งโมเดลแยกราย agent ผ่าน config โมเดลต้องรองรับ structured output / tool calling เลือกรุ่นจากราคาและผลบนชุดทดสอบตอนลงมือ |
| D11 | เมื่อโมเดลถูกไม่แม่นพอ | ความถูกต้องคงที่ ≥ 99.5% ส่งให้คนดูมากขึ้นแทน ถ้าระบบทำเองได้ต่ำเกินไป ให้ลองเปลี่ยน**เฉพาะ Verifier** เป็นโมเดลที่เก่งกว่า |
| D12 | ข้อมูลนอก template | เก็บในตาราง `extra_results` (ไม่ทิ้ง) คง template 45 คอลัมน์ไว้ตามเดิม เก็บไฟล์ต้นฉบับ และบันทึก**ที่มาของแต่ละค่า** (ไฟล์/sheet/เซลล์) |
| D13 | ข้อมูลซ้ำ/ขัดแย้ง | ค่าเท่ากัน → ข้าม / ค่าต่างกัน → เข้ารายการ "ข้อมูลขัดแย้ง" ให้คนเลือก (ค่าเดิมยังอยู่) เก็บประวัติทุกครั้งที่เปลี่ยนค่า มีปุ่ม "ยอมรับค่าใหม่ทั้งไฟล์" ตรวจเลขบัตรประชาชนด้วย **checksum หลักที่ 13** |
| D14 | โค้ด | เก็บ FastAPI / Postgres / Docker / หน้าเว็บเดิม / `mapping_config.py` (ใช้ตั้งต้นพจนานุกรมกลาง) เขียนส่วนแปลงข้อมูลใหม่เป็น **LangGraph ใน `app/pipeline/`** ย้าย `his_to_template.py`, `main.py`, `sample_his_data.py` ไป `legacy/` ใช้ **Alembic** จัดการ schema ล้างข้อมูล mock ใน DB แก้ `requirements.txt` |
| D15 | ชุดทดสอบ | **3 ชั้น:** (1) ชุดพัฒนา 15–20 รูปแบบ รู้คำตอบที่ถูกทุกค่า (2) ชุดสอบ สร้างด้วยกฎคนละแบบแล้ว**ล็อกไว้** ใช้รายงานผล (3) ชุดทดสอบแบบไม่รู้ล่วงหน้า ผู้ใช้หาคนสร้าง 2–3 ไฟล์ การให้ผู้ฟังส่งไฟล์มาลองสดตัดสินใจในสัปดาห์ที่ 3 |
| D17 | นโยบายอนุมัติอัตโนมัติ (ตัดสินใจ 2026-09-12 จากผลวัดสัปดาห์ที่ 2) | **เปิด** (`AUTO_ACCEPT=on`): ระบบรับเองเฉพาะเมื่อ AI สองค่ายตอบตรงกัน (คอลัมน์ + ตัวคูณหน่วย หรือ ปกติ/ผิดปกติ) + มั่นใจสูง + ทุกค่าในไฟล์ผ่านการตรวจช่วงค่าด้วยโค้ด ส่วน `__ignore__` และคอลัมน์ที่อาจเป็นชื่อ/แผนก ต้องให้คนตอบเสมอ ผลวัดชุดสอบ: ทำเองได้ 98.3%, คนตัดสินใจ 2 ครั้ง, ค่าผิด 0 (ถ้าปิด: 58.7%, 165 ครั้ง) |
| D16 | การรัน/ความปลอดภัย | รันบนโน้ตบุ๊กด้วย `docker compose` ไม่มีระบบล็อกอิน แต่รับการเชื่อมต่อจาก localhost เท่านั้น แก้ XSS ย้าย secrets ไป `.env` |
| D19 | API ภายนอก (ตัดสินใจ 2026-09-14) | เปิด API ให้ **ระบบ HIS ของโรงพยาบาลส่งไฟล์เข้ามาอย่างเดียว** ผ่านอินเทอร์เน็ต แล้ว deploy บน server: ชุดแยก `/api/v1` (เอกสารที่ `/api/v1/docs`) · API key รายโรงพยาบาล (เก็บแค่ hash, key ผูกรหัสโรงพยาบาล ระบบไม่เชื่อรหัสที่ผู้เรียกส่งมา) · ส่งไฟล์ได้เลขงานทันทีแล้วประมวลผลเบื้องหลัง · ดูได้แค่สถานะไฟล์ของโรงพยาบาลตัวเอง **ไม่มีทางดึงผลตรวจรายคน** · จำกัดขนาด/ชนิดไฟล์/จำนวนครั้งต่อนาที · reverse proxy HTTPS เปิดเฉพาะ `/api/v1` หน้าเว็บเจ้าหน้าที่ยังอยู่ภายใน · ใช้กับข้อมูลคนไข้จริงต้องผ่าน PDPA ก่อน |
| D20 | ย้ายหน้าใช้งานจริงมาอยู่ใน UI ใหม่ (ตัดสินใจ 2026-09-16) | งานที่ทำคือ**ย้ายหน้า `/import` เดิมมาอยู่ในหน้าตาแบบ Env-Occ เท่านั้น ไม่ได้สร้างระบบใหม่** · Walk Through Survey และรายงานผลตรวจสุขภาพกลุ่มเสี่ยง **คงเป็น mockup** ไม่ต่อฐานข้อมูล · เมนูหลักแตกเป็น **5 การ์ด**: นำเข้าผลตรวจ / งานที่ต้องตรวจ (รอตรวจ + ข้อมูลขัดแย้ง อยู่การ์ดเดียว มีเลขเตือน) / ข้อมูลพนักงาน / ภาพรวมและกราฟ / ตั้งค่า · การ์ด "ตั้งค่า" เฉพาะ admin กับ superadmin ส่วนปุ่มลบข้อมูลพนักงานทั้งหมดเฉพาะ **superadmin** และต้องพิมพ์ยืนยัน · **หน่วยบริการมาจากบัญชีที่ล็อกอิน** ไม่ให้พิมพ์รหัสเอง (superadmin เลือกจากรายชื่อที่มีจริง) ปิดช่องเดิมที่พิมพ์ผิดแล้ว `get_or_create_hospital` สร้างโรงพยาบาลใหม่เงียบ ๆ · **ตรรกะหน้ารอตรวจคงเดิมทุกอย่าง** (หลักฐาน 3 ชิ้น, ตัวเลือก 5 ทาง, ไม่มี AI เสนอ = ไม่มีปุ่มยอมรับและตั้งต้นที่ "ข้ามไว้ก่อน") เปลี่ยนแค่หน้าตา เพราะตัวเลขที่วัดไว้อ้างอิงตรรกะชุดนี้ · **Chart.js เก็บไว้ในโปรเจกต์** (`app/static/vendor/`) ไม่ดึง CDN เพราะ server อาจไม่มีเน็ตออกนอกแล้วกราฟจะหายเงียบ ๆ · หน้าเดิมเก็บไว้ชั่วคราวที่ `/import-legacy` แล้วลบเมื่อหน้าใหม่ใช้งานได้ครบ · ข้อนี้แทนที่ "ไม่มีระบบล็อกอิน" ใน D16 |
| D20-หนี้ | ยังไม่กรองข้ามโรงพยาบาล (รับความเสี่ยงไว้ 2026-09-16) | `/api/employees`, `/api/reviews`, `/api/conflicts`, `/api/stats` **ไม่กรองตามโรงพยาบาล** เจ้าหน้าที่หน่วยหนึ่งจึงเห็นชื่อ เลขบัตร ผลตรวจ และกดตัดสินใจรายการของอีกหน่วยได้ · ยอมรับได้ตอนนี้เพราะเป็น POC ข้อมูลสังเคราะห์ (D2) และมีผู้ใช้จริงคนเดียว · **ต้องแก้ก่อน**เอาข้อมูลคนไข้จริงเข้าระบบ หรือก่อนเปิดให้โรงพยาบาลที่สองใช้ ไม่ว่ากรณีไหนมาก่อน · ตรงข้ามกับโมดูลขึ้นทะเบียนหน่วยบริการที่กันข้ามหน่วยไว้แล้ว · **D23 ทำให้หนักขึ้น**: ทะเบียนสถานประกอบการเป็นทะเบียนกลาง รพ.แห่งหนึ่งจึงเห็นรายชื่อลูกค้าของอีกแห่งด้วย |
| D18 | `ID แผนก` (ตัดสินใจ 2026-09-12 จากชุด blind) | ต้องเป็น**รหัส** ถ้าไฟล์เขียนเป็นรหัสอยู่แล้ว (อังกฤษ/ตัวเลข เช่น `PROD-01`) ใช้ได้ทันที ถ้าเขียนเป็นชื่อ ("ฝ่ายผลิต") ครั้งแรกระบบจะถามรหัสแล้วจำแยกรายโรงพยาบาล ห้ามเดา · **D23 แทนที่ข้อนี้**: แผนกกลายเป็นแถวจริงที่ผูกกับสถานประกอบการ คำถามจึงเปลี่ยนจาก "รหัสอะไร" เป็น "ตรงกับแผนกไหนของบริษัทนี้" |
| D21 | ชั้นรายงานและส่งเข้ากรมฯ (ตัดสินใจ 2026-09-16) | ต่อยอดจากผลลัพธ์ 45 คอลัมน์โดย**ไม่แตะไพป์ไลน์และไม่ขอให้ HIS ปรับอะไร** · สรุปตาม **หน่วยบริการ + รอบปี + แผนก** · ปุ่มส่งทำสองอย่าง: เตรียมชุดส่ง (snapshot ความครบถ้วน/แผนก/สิ่งที่พบ/งานค้าง + sha256) และบันทึกสถานะลง `report_submissions` · ถ้ามีงานค้าง (รอตรวจ/ขัดแย้ง/คนไม่มีชื่อ) **เตือนชัดเจนแต่ยังส่งได้ถ้ายืนยัน** · คนที่ไม่มีชื่อ-นามสกุลแยกไปแท็บ "รอยืนยันชื่อ" ไม่ปนกับรายชื่อปกติ |

## สถาปัตยกรรม (สรุป)

Node ที่เป็นโค้ด (🔧) ให้ผลเหมือนเดิมทุกครั้ง ส่วน agent (🤖) ใช้เฉพาะจุดที่ต้องใช้วิจารณญาณ

```
upload → 🔧 parse_file → 🤖 profiler (ไฟล์รูปแบบใหม่ → สเปคการอ่านไฟล์ บันทึกไว้ใช้ซ้ำรายโรงพยาบาล)
       → 🔧 exact_map (mapping ของโรงพยาบาลนั้น → พจนานุกรมกลาง)
       → 🤖 mapper → 🔧 range_check → 🤖 verifier ─(ไม่เห็นด้วย, สูงสุด 1 รอบ)→ mapper
       → 👤 human_review (LangGraph interrupt + หน้าจอยืนยันที่แสดงหลักฐาน)
       → 🔧 transform_validate (CID checksum, วันที่, หน่วย, ตรวจข้อมูลขัดแย้ง)
       → [🤖 comment_classifier ‖ 🤖 qc_agent]  (รันพร้อมกัน)
       → 🔧 save_db (+ extra_results, ที่มาของค่า, ประวัติการเปลี่ยนค่า)
```

- Checkpointer: Postgres ตัวเดียวกับแอป เพื่อให้ graph ที่หยุดรอคนยืนยันทำงานต่อได้หลัง restart
- Graph state เก็บแค่ ID และข้อมูลที่ไม่ระบุตัวตน ข้อมูลรายคนอยู่ใน DB
- AI ได้รับเฉพาะหัวคอลัมน์ ชื่อ lab หน่วย และค่าตัวอย่าง ไม่ได้รับชื่อหรือเลขบัตร
- Verifier ไม่เห็นเหตุผลของ Mapper เพื่อให้ตรวจได้อิสระ
- บันทึกทุกการตัดสินใจ (agent ไหนเสนออะไร ใครยืนยัน เมื่อไหร่) ลงตารางของเราเอง ไม่ส่ง trace ออกไปภายนอก

## แผน 3 สัปดาห์

**สัปดาห์ 1: รากฐาน + การวัดผล**
- แก้ `requirements.txt`, ตั้ง Alembic, ออกแบบ schema ใหม่ (`hospitals`, `source_files`, ที่มาของค่า, `extra_results`, `conflicts`, `value_history`, `pending_reviews`, mapping สองชั้น)
- ย้ายโค้ดรุ่นเก่าไป `legacy/`, ย้าย secrets ไป `.env`
- Node ที่เป็นโค้ด: parse, normalize, validate, CID checksum, ตรวจข้อมูลขัดแย้ง (แก้บั๊กจากรีวิวไปพร้อมกัน)
- สคริปต์สร้างชุดพัฒนา + ชุดสอบ (ล็อก) + สคริปต์วัดผล พร้อมวัด **baseline ของวิธี fuzzy เดิม**
- ตัวเชื่อมต่อ OpenRouter ที่ตั้งโมเดลแยกราย agent

**สัปดาห์ 2: Agent หลัก**
- LangGraph graph + Postgres checkpointer + interrupt
- Profiler, Mapper, range_check, Verifier
- หน้าจอยืนยันที่แสดงหลักฐาน + API สำหรับ resume graph
- รอบวัดผลบนชุดพัฒนา → เลือกโมเดล → วัดบนชุดสอบรอบแรก

**สัปดาห์ 3: ส่วนเสริม + เตรียมนำเสนอ**
- QC agent, Comment classifier, หน้ารายการข้อมูลขัดแย้ง
- Dashboard: ความถูกต้อง, สัดส่วนงานที่ทำเองได้, ต้นทุนต่อไฟล์, ตัวคำนวณเวลาที่ประหยัด
- โหมด replay, แก้ XSS, จำกัดการเชื่อมต่อที่ localhost
- ทดสอบด้วยชุดทดสอบแบบไม่รู้ล่วงหน้า → ตัดสินใจเรื่องให้ผู้ฟังส่งไฟล์มาลองสด
- ซ้อม demo

## นอกขอบเขต POC (Roadmap เฟส 2)

- ไฟล์ PDF, รูปถ่าย/สแกน (OCR), เชื่อมต่อ HIS โดยตรง / HL7 / FHIR

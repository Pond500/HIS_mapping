# แผนงาน D23 — ปรับโครงเก็บข้อมูลให้ตรงกับ DATA DICTIONARY ของกรมฯ

ข้อตกลงอยู่ใน [requirements.md](requirements.md) D23, D23-ก, D23-หนี้, D23-ถาม, D19-หนี้
เอกสารอ้างอิง [DATA_DICTIONARY.md](DATA_DICTIONARY.md)

**เสร็จเมื่อ** เดินครบ flow ตั้งแต่สร้างบริษัทจนส่งออกไฟล์ได้ ด้วยสามไฟล์จริงที่เทสไปแล้ว
พร้อมรายงานว่าแต่ละขั้นได้หรือไม่ได้อะไรบ้าง

---

## กับดักชื่อซ้ำ ต้องรู้ก่อนอ่านทั้งแผน

ตาราง `employees` ของเราวันนี้ **ไม่ใช่** `employees` ของกรมฯ

| | ของเราวันนี้ | ของกรมฯ |
|---|---|---|
| ความหมาย | หนึ่งคน + หนึ่งวันที่ตรวจ + ผล 40 ช่อง | ทะเบียนคน ไม่มีผลตรวจเลย |
| คีย์ | (cid, visit_date) | (citizen_id, department_id) |

migration จึง **เปลี่ยนชื่อของเก่าทิ้งก่อน** แล้วค่อยสร้าง `employees` ตัวใหม่
ห้าม `ALTER` ของเก่าให้กลายเป็นของใหม่ เพราะความหมายคนละอย่าง

---

## สายโซ่ใหม่

```
companies ──< departments ──< employees ──< employee_checkups
    │                                              │
    └──< walkthrough_surveys ──< employee_checkup_batches ──┘
                                        │
                              employee_checkup_types
```

อ่านจากขวา: ผลตรวจหนึ่งแถวต้องมีคนในทะเบียนและรอบตรวจ
รอบตรวจต้องมีการสำรวจและประเภทการตรวจ การสำรวจต้องมีบริษัท

## ขั้นที่ 1 — โครงข้อมูล (ไม่แตะ UI)

### 1.1 migration `0008_ddc_schema`

เขียนมือ ไม่ใช้ autogenerate เพราะมีการเปลี่ยนชื่อตารางที่ autogenerate จะตีความเป็น drop+create

1. `DELETE` ข้อมูลทดสอบทั้งหมด (D23: ล้างทิ้ง) — employees, value_provenance,
   extra_results, conflicts, value_history, pending_reviews, agent_decisions,
   report_submissions, source_files
   **ไม่ลบ** hospitals, lab_mappings (พจนานุกรมที่เรียนมา), comment_labels, app_users, api_keys
2. `DROP TABLE employees` ของเก่า (ล้างแล้วจึงไม่มีอะไรหาย)
3. สร้างใหม่ตามลำดับ FK:
   `companies` → `departments` → `walkthrough_surveys` → `employee_checkup_types`
   → `employee_checkup_batches` → `employees` → `employee_checkups`
   → `checkup_categories` → `checkup_lists`
4. `value_provenance`, `conflicts`, `value_history` เปลี่ยน FK จาก `employee_id`
   ไปเป็น `checkup_id` (ชี้ `employee_checkups`)
5. `extra_results` เปลี่ยนจากคีย์ (cid, visit_date) ไปผูก `checkup_id`
6. seed `employee_checkup_types` 3 แถว, `checkup_categories` ตาม `Field.group`
7. seed `checkup_lists` จาก `TEMPLATE_FIELDS` — `name`, `unit`, `column_name`
   **`lower_limit`/`upper_limit` เว้น NULL** จนกว่ากรมฯ จะให้เกณฑ์มา

### 1.2 ผ่อนข้อบังคับที่ไฟล์แล็บไม่มีทางรู้

ใน `employees` ของเรา คอลัมน์เหล่านี้เป็น **nullable** แม้ data dic บอก NOT NULL:
`gender`, `birth_year`, `nationality`, `work_experience`, `position`
เพราะทางเลือกเดียวที่เหลือคือเดาค่า ซึ่งขัดกฎเหล็ก
แถวที่ยังไม่ครบขึ้นสถานะ "ทะเบียนไม่ครบ" และตอนส่งออกจะถูกกันไว้ให้เห็น

`firstname`/`lastname` เป็น NOT NULL ตามเขาได้ เพราะไฟล์ทะเบียนต้องมีชื่ออยู่แล้ว
(ปัญหา "คนไม่มีชื่อ" ที่เคยเจอ หายไปเองเพราะทะเบียนมาก่อนผลตรวจ)

### 1.3 หน่วยและรหัส

แปลงตอนเขียนลง `employee_checkups` ไม่ใช่ใน `template.py`:
`wbc`, `plt` ÷1000 → `10^3/uL` · `rbc_che` → `U/g Hb`
`chest_xray`, `ekg`, `hearing_ability`, `far_vision_test` → 1/2 กลายเป็น 0/1
**ค่าดิบเดิมยังอยู่ครบใน `value_provenance.raw_value`** ถ้ากรมฯ ตอบกลับว่าเราเข้าใจผิด ย้อนได้

### 1.4 view `v_employee_results_45`

join `employees` + `employee_checkups` + `employee_checkup_batches` กลับเป็นหน้าตา
45 คอลัมน์แบบเดิม มีไว้เพื่อ **เปิดการวัดผลกลับมาได้โดยไม่ต้องแก้ `truth.json`** (D23-หนี้)
ทำพร้อม migration ตอนนี้ ราคาถูกกว่ามาทำทีหลังมาก

## ขั้นที่ 2 — ไพป์ไลน์

ไพป์ไลน์ **ไม่เปลี่ยน** `reader → profiler → mapper → extract` ยังผลิต `Extraction`
ที่คีย์ด้วย (cid, วันที่) เหมือนเดิม งานทั้งหมดอยู่ที่ `store.py` ซึ่งกลายเป็น adapter

### 2.1 `template.py` รองรับสองชุด

`TEMPLATE_FIELDS` เดิม = ชุดผลตรวจ
เพิ่ม `REGISTRY_FIELDS` = ชุดทะเบียน (cid, ชื่อ, สกุล, คำนำหน้า, เพศ, ปีเกิด, สัญชาติ,
ตำแหน่ง, อายุงาน, โรคประจำตัว, แผนก)
`Extraction` และ `pending_reviews` พก `field_set` บอกว่ากำลังคุยถึงชุดไหน
หน้ารีวิวอ่านค่านี้เพื่อเลือกรายการคอลัมน์ที่เสนอให้คนกด

### 2.2 `store.py` เขียนลงสามตาราง

รับ `batch_id` เพิ่มเข้ามา แล้ว:

```
ต่อหนึ่ง cid ในไฟล์:
  หา employees จาก (citizen_id, department ที่ผูกกับบริษัทของรอบนี้)
  ไม่เจอ           -> review kind="unregistered_person"  ไม่เขียนผลตรวจแถวนี้   [บล็อก]
  เจอ แต่คนละแผนก  -> review kind="department_change"     ไม่เขียนผลตรวจแถวนี้
  เจอ              -> upsert employee_checkups (employee_id, batch_id)
                      ค่าใหม่        -> เขียน + ValueProvenance(checkup_id, column)
                      ค่าเดิมเท่ากัน -> ข้าม
                      ค่าต่าง        -> Conflict (ค่าเดิมยังอยู่)
```

`checkup_date` รายคนใช้วันที่ในไฟล์ถ้ามี ไม่มีก็ปล่อย NULL
วันที่ที่ใช้อ้างอิงจริงคือ `appoint_date` ของรอบ

คอลัมน์ที่ไม่มีใน `employee_checkups` ลง `extra_results` ผูก `checkup_id`

### 2.3 review ชนิดใหม่สองชนิด

| kind | เกิดเมื่อ | หน้าจอแสดง | ตัวเลือก |
|---|---|---|---|
| `unregistered_person` | cid ไม่มีในทะเบียนของบริษัทนี้ | เลขบัตร ชื่อในไฟล์ จำนวนค่าที่รออยู่ | เพิ่มเข้าทะเบียน / ข้ามคนนี้ / ข้ามไว้ก่อน |
| `department_change` | แผนกในไฟล์ ≠ แผนกในทะเบียน | แผนกทะเบียน เทียบ แผนกในไฟล์ | ย้ายแผนกจริง / ไฟล์เขียนผิด ใช้ทะเบียน / ข้ามไว้ก่อน |

ตรรกะหน้ารอตรวจเดิม (หลักฐาน 3 ชิ้น, ตั้งต้นที่ "ข้ามไว้ก่อน") **คงเดิมทุกอย่าง**
`department` review ของ D18 ถูกแทนที่ด้วย `department_change`

### 2.4 ปิด `/api/v1`

ถอด mount ออกจาก `app/main.py` ทิ้งคอมเมนต์ชี้ D19-หนี้ ไม่ลบโค้ด

## ขั้นที่ 3 — UI ไล่ขึ้นมา หน้าตา Env-Occ คงเดิม

ทำทีละหน้า แต่ละหน้าใช้งานได้จริงก่อนขึ้นหน้าถัดไป

| ลำดับ | หน้า | ทำอะไร |
|---|---|---|
| 3.1 | ทะเบียนสถานประกอบการ | เพิ่ม/แก้บริษัท (เลขนิติบุคคล ชื่อ สาขา ที่อยู่) + รายชื่อแผนก |
| 3.2 | Walkthrough (ย่อ) | สร้างหัวการสำรวจ: บริษัท วันที่ ผู้สำรวจ หมายเหตุ · แบบสอบถามความเสี่ยงเต็มยังเป็น mockup |
| 3.3 | รอบตรวจ | เลือกบริษัท + การสำรวจ + ประเภทการตรวจ + วันนัด · ปุ่ม "รับรองผลทั้งรอบ" |
| 3.4 | นำเข้าทะเบียนพนักงาน (AI) | อัปไฟล์รายชื่อ ผ่านไพป์ไลน์เดิมด้วย `REGISTRY_FIELDS` |
| 3.5 | นำเข้าผลตรวจ (AI) | กล่องอัปโหลดเลือกรอบก่อน แล้วอัปไฟล์ |
| 3.6 | งานที่ต้องตรวจ | เพิ่ม review สองชนิดใหม่ |
| 3.7 | ข้อมูลพนักงาน | อ่านจากโครงใหม่ แท็บ "ทะเบียนไม่ครบ" แทนแท็บ "รอยืนยันชื่อ" เดิม |
| 3.8 | ภาพรวม + ส่งเข้ากรมฯ | สรุปตามรอบ · ส่งออกเป็นไฟล์ตามโครง `employees` + `employee_checkups` |
| 3.9 | กรอกผลทีละคน | ฟอร์มรายคนในรอบ บันทึกผ่าน `value_history` ว่าใครแก้ |

# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Converts Thai hospital information system (HIS) health-check data (occupational health / อาชีวอนามัย) into a fixed 45-column "result template". HIS data is usually Long/EAV (one row per lab result); the template is Wide (one row per person + visit date). Much of the code, comments, UI text and error messages are in Thai. Keep that as it is.

**Direction:** this is being rebuilt as a POC that takes in any CSV/XLSX layout through a LangGraph multi-agent pipeline (OpenRouter, cheap models) with human review. The agreed requirements, decisions (D1–D16) and the 3-week plan are in [docs/requirements.md](docs/requirements.md). Read it before making design changes. The core rule is that every value is either correct or flagged for a human, so nothing wrong is saved silently.

## Commands

Python 3.12. Config comes from `.env`, which is gitignored. Copy it from `.env.example`. `DATABASE_URL` is required and uses the psycopg3 driver (`postgresql+psycopg://`).

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
docker compose up -d --build               # Postgres + app, both bound to 127.0.0.1 (app on :8000)
docker compose up -d postgres              # DB only, then run the app locally for --reload:
.venv/bin/uvicorn app.main:app --reload    # run from repo root
.venv/bin/python legacy/main.py            # old standalone CLI pipeline (no DB needed)
```

```bash
.venv/bin/python -m pytest -q tests                            # all tests
.venv/bin/python -m pytest -q tests/test_testgen.py::test_dev_set_consistent   # one test
.venv/bin/python -m testgen.build dev                          # regenerate the dev test set
.venv/bin/python -m testgen.selfcheck dev                      # generator sanity check
.venv/bin/python -m testgen.build --verify exam                # exam set unchanged?
.venv/bin/python -m evaluation.run --sut baseline --set dev    # score a system on all dev cases
.venv/bin/python -m evaluation.run --case d08_extras_traps -v  # one case, with error examples
```

**Evaluation** (`evaluation/`): `run.py` uploads each case into a separate DB (`his_mapping_eval`, wiped per case) through a SUT adapter (`SUTS`; `baseline` = the old `/api/upload`), then `metrics.py` sorts every expected cell into correct / wrong / missing_flagged / missing_silent, plus spurious. Headline metrics map to requirement D8: auto_precision ≥ 99.5%, automation ≥ 70%, automation_repeat ≥ 95%, silent_errors = 0. A pipeline shows it "asked a human" only through open `pending_reviews` rows whose payload follows the convention in the `metrics.py` docstring. New pipelines must follow that convention or they get no credit for flagging. Results are saved to `evaluation/results/`.

**Test data** (`testdata/`, generated by `testgen/`, see testdata/README.md): `dev/` (18 cases) is for tuning. `exam/` (9 cases) is **locked** by `LOCK.json`, is generated from held-out vocabulary pools (`testgen/vocab.py` `*_EXAM`), and must never be used to tune prompts or code. Only report numbers from it. Each case's `truth.json` gives the expected final DB state, conflicts, flagged items, extras and derived values. Don't hand-edit files there. Change `testgen/` and rebuild instead. Rebuilding exam needs `--force` and a reason in the commit message.

`legacy/` holds the pre-POC CLI pipeline and the old ad-hoc `test_*.py` scripts, which write real rows to the live DB. The original mock files are in `mock_data/original/`. Uploaded originals are kept in `storage/uploads/` (gitignored, mounted into the app container).

```bash
.venv/bin/alembic check                                        # models and DB in sync?
```

## Architecture

There are two separate code paths that share `mapping_config.py`:

1. **Legacy CLI pipeline** (`legacy/`): `main.py` → `his_to_template.py` (`run_pipeline`: load → map lab names → pivot to wide → transform values, e.g. Normal→1/Abnormal→2 and CE→BE dates → export Excel with openpyxl). Input comes from the in-memory fixtures in `sample_his_data.py`.

2. **FastAPI web app** (`app/`): upload CSV/XLSX → map → upsert into Postgres → dashboard/export. The web app does **not** use `his_to_template.py`. It reimplements the logic in `app/routes/upload.py`:
   - `detect_file_format` decides long vs wide from column names. Each XLSX sheet is detected and processed on its own.
   - `convert_long_to_wide` normalizes HIS column aliases (cid/pid/vstdate/…), maps `lab_name` to a template column, splits BP values like `"120/80"` into systolic and diastolic, applies `unit_factor`, and pivots on (cid, visit_date).
   - `process_wide_dataframe` maps each column to a DB column in this order: `TEMPLATE_TO_DB` exact match (Thai template headers → English DB names), then a direct DB column name, then a DB mapping or fuzzy match. It validates values per row (numeric, categorical 1/2, dates where a year > 2500 is treated as Buddhist Era) and **upserts** on `(cid, visit_date)`. Row errors are collected as Thai messages and are not raised.
   - Lab-name mapping goes through `get_mapped_col`: an exact lowercase match against the `lab_mappings` table, then a RapidFuzz `token_sort_ratio` fallback at ≥ 85.

### Template, schema and mappings

- `app/template.py` is the **single source of truth** for the 45 template columns: DB name, template header, kind (id/text/date/numeric/categorical) and precision. The `Employee` model columns, the export headers and the field sets in `upload.py` are all derived from it.
- `app/models.py` holds all tables. `app/database.py` only has the engine, session and `Base`. The schema is managed **only by Alembic** (`alembic/versions/`). There is no `create_all` and no `init.sql`. The tables are hospitals, source_files, file_profiles, lab_mappings, employees, value_provenance, extra_results, conflicts, value_history, pending_reviews and agent_decisions. docs/requirements.md D6/D12/D13 explains why each one exists.
- `lab_mappings` has two layers: `hospital_id IS NULL` is the central dictionary, and a non-null value is a hospital override. `target_column` is a template column, or `__extra__`/`__ignore__`. Migration `0002_seed` seeds the central layer from a **frozen snapshot** of `mapping_config.LAB_NAME_TO_TEMPLATE`, so editing `mapping_config.py` does not change the DB. It also creates the `UNSPECIFIED` hospital, which uploads use until a hospital picker exists.
- `profusion` is text (ILO values like `"1/0"`), not numeric.

### Frontend

A single page, `app/templates/index.html`, with vanilla JS and `app/static/css/style.css`. It calls the JSON API: `/api/upload`, `/api/stats`, `/api/employees`, `/api/upload-logs`, `/api/export`, `/api/mappings`.

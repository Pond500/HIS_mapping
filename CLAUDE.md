# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Converts Thai hospital information system (HIS) health-check data (occupational health / อาชีวอนามัย) into a fixed 45-column "result template". HIS data is usually Long/EAV (one row per lab result); the template is Wide (one row per person + visit date). Much of the code, comments, UI text and error messages are in Thai. Keep that as it is.

**Direction:** this is being rebuilt as a POC that takes in any CSV/XLSX layout through a LangGraph multi-agent pipeline (OpenRouter, cheap models) with human review. The agreed requirements, decisions (D1–D16) and the 3-week plan are in [docs/requirements.md](docs/requirements.md). Read it before making design changes. The core rule is that every value is either correct or flagged for a human, so nothing wrong is saved silently.

## Commands

Python 3.12. Config comes from `.env`, which is gitignored. Copy it from `.env.example`. `DATABASE_URL` is required and uses the psycopg3 driver (`postgresql+psycopg://`).

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
docker compose up -d --build               # Postgres + app, both bound to 127.0.0.1 (app on :8000)
docker compose up -d postgres              # DB only, then run the app locally for --reload:
.venv/bin/uvicorn app.main:app --reload    # run from repo root
.venv/bin/python legacy/main.py            # old standalone CLI pipeline (no DB needed)
```

```bash
.venv/bin/python -m pytest -q tests                            # all tests
.venv/bin/python -m pytest -q tests/test_testgen.py::test_dev_set_consistent   # one test
.venv/bin/python -m testgen.build dev                          # regenerate the dev test set
.venv/bin/python -m testgen.selfcheck dev                      # generator sanity check
.venv/bin/python -m testgen.build --verify exam                # exam set unchanged?
.venv/bin/python -m evaluation.run --sut rules --set dev       # score a system on all dev cases (no LLM)
.venv/bin/python -m evaluation.run --sut agents --set dev --oracle   # agent graph + simulated reviewer (costs cents)
.venv/bin/python -m evaluation.run --sut agents --case d08_extras_traps -v  # one case, with error examples
.venv/bin/python -m evaluation.bench_mapper --models google/gemini-3.1-flash-lite deepseek/deepseek-v4-flash   # compare LLMs (dev, costs cents)
```

**Evaluation** (`evaluation/`): `run.py` uploads each case into a separate DB (`his_mapping_eval`, wiped per case) through a SUT adapter (`SUTS`: `baseline` = `/api/legacy/upload`, `rules` = pipeline without LLM, `agents` = the LangGraph graph with `AUTO_ACCEPT=on`, `agents_noauto` = every AI proposal waits for a human), then `metrics.py` sorts every expected cell into correct / wrong / missing_flagged / missing_silent, plus spurious. Headline metrics map to requirement D8: auto_precision ≥ 99.5%, automation ≥ 70%, automation_repeat ≥ 95%, silent_errors = 0. A pipeline shows it "asked a human" only through open `pending_reviews` rows whose payload follows the convention in the `metrics.py` docstring. New pipelines must follow that convention or they get no credit for flagging. With `--oracle`, a simulated perfect reviewer answers each file's open mapping reviews from the truth after the file is uploaded. **Automation is scored per upload before the oracle answers**, while precision and silent errors are scored on the final state. That is how the "same hospital, second file ≥ 95%" target is measured. `reset_db` must wipe **every** learned table between cases (mappings, hospitals, `comment_labels`); until 2026-09-13 it missed `comment_labels`, so finding meanings leaked between cases and earlier agent numbers for comments were inflated. Two evals must not share a DB. For a parallel run, set a different `EVAL_DATABASE_URL` and `STORAGE_DIR`. Results are saved to `evaluation/results/`.

**Test data** (`testdata/`, generated by `testgen/`, see testdata/README.md): `dev/` (22 cases) is for tuning. `exam/` (9 cases) is **locked** by `LOCK.json`, is generated from held-out vocabulary pools (`testgen/vocab.py` `*_EXAM`), and must never be used to tune prompts or code. Only report numbers from it. `testdata/blind/` (4 cases built by `evaluation/blind.py` from the externally made `blind_test_datasets/`, where only the answer keys are read) is locked the same way. It was measured once before any fix (results committed); numbers after the 2026-09-12 fixes are no longer blind. `evaluation/blind_triage.py` classifies every miss as a system bug or an answer-key issue (`--export` writes the answer-key cells for the test creator). Each case's `truth.json` gives the expected final DB state, conflicts, flagged items, extras and derived values. Don't hand-edit files there. Change `testgen/` and rebuild instead. Rebuilding exam needs `--force` and a reason in the commit message.

**Live demo** ([docs/demo.md](docs/demo.md)): every successful LLM answer is recorded in `storage/llm_cache/`. `LLM_MODE=live` (the default) calls the model and records the answer. `fallback` calls the model first and, on a provider/network error or `LLM_TIMEOUT_S`, uses the recording immediately. `replay` never touches the network. When there is no recording, the call raises `LLMError` and the item goes to a human. After a rehearsal, run `python scripts/reset_demo.py --yes`. It wipes data and learned mappings but keeps the seeded dictionary and the recordings. It needs `--yes` because it deletes everything in the database `DATABASE_URL` points to.

**Don't run `docker compose up --build` while an evaluation or a long upload is running.** It can recreate the Postgres container, which kills every open connection (this happened on 2026-09-12 and broke two eval runs).

`legacy/` holds the pre-POC CLI pipeline and the old ad-hoc `test_*.py` scripts, which write real rows to the live DB. The original mock files are in `mock_data/original/`. Uploaded originals are kept in `storage/uploads/` (gitignored, mounted into the app container).

```bash
.venv/bin/alembic upgrade head                                 # apply migrations (the app container does this on start)
.venv/bin/alembic revision --autogenerate -m "..."             # after changing app/models.py
.venv/bin/alembic check                                        # models and DB in sync?
```

**Always read an autogenerated migration before running `upgrade`.** LangGraph's `checkpoint*` tables live in the same database but are not in our metadata. On 2026-09-12 an autogenerate proposed dropping them and was applied to the dev DB. `alembic/env.py::include_object` now skips tables that aren't ours, but still check for `drop_table`.

## Architecture

**Upload flow:** `POST /api/upload` (`app/routes/upload.py`, form field `file`) needs a staff session and takes the hospital from the signed-in account, never from the request (D20): only a superadmin may send a `hospital` form field, and only a code that already exists, so a typo can no longer create a hospital and scatter the learned mappings. It calls `register_file`, which stores the original bytes in `storage/uploads/<sha256>.<ext>` and registers a `SourceFile`. It then runs the agent graph through `app/graph/service.py::run_upload`. Every store step is one transaction per file: it lands completely or is rolled back and marked `failed`. The app port defaults to 8000 (`APP_PORT` in `.env`; this machine uses 8100 because 8000 is taken).

**Agent graph** (`app/graph/flow.py`, one LangGraph thread `file-<id>` per file, checkpointed in Postgres through a `psycopg_pool` pool so it survives DB restarts). The flow is `analyze → mapper → check → verifier ⇄ (one revision) → decide → store → human [interrupt] → store`.
- `analyze` collects the labels the rules can't resolve, with their sample and numeric values. Graph state holds **no names or CIDs**.
- `check` is code, not the LLM. Every value in the file must fit the proposed column's plausible range after unit conversion.
- `decide` auto-accepts a proposal (saved as a hospital `LabMapping` with `origin="agent_auto"`) only when `AUTO_ACCEPT=on`, the Mapper's confidence is high, the Verifier's own target and factor match, and `check` passed. `__ignore__` always goes to a human, because ignoring by mistake is a silent drop.
- `store` runs the rules pipeline with the current mappings. It stores what is certain now, and mapping reviews carry the agent evidence (`proposal`, `verification`, `range_ok`).
- `human` pauses with `interrupt()`. `service.decide()` resumes it with decisions, or applies them and re-runs `process_file` if the graph has already finished. Re-processing a file is idempotent.

Learned mappings (`origin` in `human` / `agent_approved` / `agent_auto`) are keyed by the exact (label, unit) seen in the file and store the **total** factor.

**External API** (D19, [docs/api.md](docs/api.md)): hospital HIS systems send files to `/api/v1` (`app/routes/api_v1.py`, its own FastAPI app mounted at `/api/v1`, with docs at `/api/v1/docs`). Callers authenticate with an `X-API-Key` header (`app/api_keys.py`). Only the SHA-256 of a key is stored. A key belongs to one hospital, so the hospital a file is filed under comes from the key, never from the request. `POST /files` registers the file and answers 202 at once. `service.run_upload` then runs as a background task, at most `API_MAX_PARALLEL` at a time. On startup, files still `processing` are run again (`resume_unfinished`). Sending the same bytes again returns the earlier file. Callers can only read the status of their own hospital's files, never people's results. Keys are managed with `scripts/manage_api_keys.py`. Only `/api/v1` may be exposed to the internet ([deploy/Caddyfile](deploy/Caddyfile)). All the other `/api/...` routes belong to the staff page and have no authentication. Rate limiting and the background queue are in-process, so run one app process.

**Review API** (`app/routes/reviews.py`): `GET /api/reviews?status=open&file_id=`, `GET /api/files/{id}`, `POST /api/files/{id}/decisions` (actions `approve` / `set` target+unit / `extra` / `ignore` / `skip`), and `GET /api/template/columns`.

**Pipeline** (`app/pipeline/`, rules only, no LLM; the graph wraps it):
1. `reader.py` turns bytes into `Sheet`s of raw cells. It handles CSV (encoding tried in order utf-8-sig/utf-8/cp874/utf-16, delimiter sniffed), XLSX (openpyxl) and XLS (xlrd).
2. `profiler.py` produces a `SheetSpec` per sheet: layout long/wide/transposed/skip, the header row, identity columns, and the lab/result/unit columns or unit row. It finds the CID and date columns **by content first** and uses header `ALIASES` second. A sheet it can't read produces `problems`, which become a `profile` review.
3. `mapper.py` resolves a label (long: lab name; wide: header) with exact matches only, in this order: hospital mapping, then the template's own column names, then the central dictionary. There is **no fuzzy matching**. A unit given in parentheses, a unit column/row or an inline unit is converted with `units.py` (standard clinical conversions). An unknown or incompatible unit leaves the label unresolved. For example, "FVC (% Pred)" is not mapped to FVC in litres.
4. `extract.py` turns each cell into a canonical value or a review item. Review kinds: `mapping` (unknown label, unknown unit, or ≥20% of a label's values outside the plausible range in `app/template.py`), `value` (censored `<0.1`, unparseable, out of range, or two different values for one cell in the same file), `cid` (checksum failed: the whole row is skipped), `comment` (only comment text, no 1/2 column), `identity` (the profiler couldn't find the name/department column(s) and lists unrecognized text columns as candidates; the answer is saved as a hospital `LabMapping` with `target_column="__id:<role>"`, keyed by `profiler.hkey(header)`, and later passed to `profile_sheet(..., id_aliases)`), `department` (D18: a department written as a name needs its code once per hospital; saved as a hospital `LabMapping` with `target_column="__dept:<code>"`; values that already look like codes pass), and `profile`. `identity` can also ask for `visit_date` when the only date is in the report title (`profiler.title_date` / `file_title_date`): the reviewer confirms once per hospital (saved as the `__report_title_date__` identity alias), and the date is never used unconfirmed. A finding written in a category column ("Fibrosis RUL") becomes a `comment` review; once its meaning is learned, 2 = abnormal also stores the text as the comment. Names go through `normalize.split_full_name`/`clean_name`, which strip single or combined titles ("นาง/นางสาว") and raise `Unparseable` rather than store a leftover like "/นางสาว…". A scientific-notation CID with fewer than 13 significant digits ("1.10046E+12") is never trusted. An unfound identity column must **never** be skipped silently: in a long file an unknown column isn't read at all, so only the `identity` review makes the loss visible (dev cases d19/d20).
5. `store.py` writes the result. A new cell is stored with `ValueProvenance`. The same value again is skipped. A different value becomes an open `Conflict`, and the stored value is never overwritten silently.

`app/pipeline/normalize.py` holds the value parsers: CID checksum, CE/BE dates in many formats, numbers, categorical, BP, and Thai names. It raises `Unparseable` instead of guessing.

**LLM agents** (`app/llm/`, `app/agents/`): all calls go through `app/llm/client.py::call_structured`. It uses OpenRouter via the `openai` SDK with a strict `json_schema` response format, and passes `provider.require_parameters` and `data_collection: deny`. Answers are validated with pydantic and retried with the validation error. Failures raise `LLMError`, and the caller must then flag for a human. Calls are logged to `agent_decisions` when a session is given. The model for each agent is set in `app/llm/config.py` and can be overridden with env `LLM_MODEL_<AGENT>`. Pin exact model ids. The API key is read from the project `.env` first, **ahead of** the shell environment. `app/agents/catalog.py` describes each column for prompts. Agents never produce stored numbers. For example, the Mapper agent returns a target plus the unit the values are written in, and `units.py` computes the factor.

`app/routes/upload_legacy.py` (`/api/legacy/upload`) is the old exact+RapidFuzz code. It is kept **only** so the `baseline` evaluation SUT can be re-run. Don't extend it.

### Template, schema and mappings

- `app/template.py` is the **single source of truth** for the 45 template columns: DB name, template header, kind (id/text/date/numeric/categorical) and precision. The `Employee` model columns, the export headers and the field sets in `upload.py` are all derived from it.
- `app/models.py` holds all tables. `app/database.py` only has the engine, session and `Base`. The schema is managed **only by Alembic** (`alembic/versions/`). There is no `create_all` and no `init.sql`. The tables are hospitals, source_files, file_profiles, lab_mappings, employees, value_provenance, extra_results, conflicts, value_history, pending_reviews and agent_decisions. docs/requirements.md D6/D12/D13 explains why each one exists.
- `lab_mappings` has two layers: `hospital_id IS NULL` is the central dictionary, and a non-null value is a hospital override. `target_column` is a template column, or `__extra__`/`__ignore__`. Migration `0002_seed` seeds the central layer from a **frozen snapshot** of `mapping_config.LAB_NAME_TO_TEMPLATE`, so editing `mapping_config.py` does not change the DB. It also creates the `UNSPECIFIED` hospital, which uploads use until a hospital picker exists.
- `profusion` is text (ILO values like `"1/0"`), not numeric.

### Frontend

A single page, `app/templates/index.html`, with vanilla JS and `app/static/css/style.css`. It calls the JSON API: `/api/upload` (with a hospital code), the review endpoints (the "รอตรวจ" tab shows the evidence for each item and posts decisions), `/api/stats`, `/api/employees`, `/api/upload-logs`, `/api/export` and `/api/mappings`. **Every value from a file or from an LLM that is rendered with `innerHTML` must go through `esc()`** (D16).
